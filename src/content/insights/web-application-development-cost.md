"How much does a web app cost?" has no honest single answer. Two applications with the same name — *customer portal*, *booking system*, *dashboard* — can differ in cost by ten times, because the work is driven by scope details that are invisible in a one-line brief.

This guide explains the factors that move the number so you can plan a budget, compare proposals fairly and avoid surprises.

## The main cost drivers

### 1. Number of user roles

Every role — customer, staff, manager, admin, partner — needs its own permissions, screens and test cases. A single-role internal tool is much simpler than a system where five roles see different versions of the same data.

### 2. Workflow complexity

Count the states a record can be in and the rules that move it between them. Approvals, deadlines, escalations, partial payments and reversals multiply both build and testing effort.

### 3. Integrations

Each external system — payment gateway, accounting software, SMS, email, government APIs, legacy databases — adds design, error-handling and maintenance work. Poorly documented APIs add the most uncertainty.

### 4. Data migration

Moving records from spreadsheets or an old system is often underestimated. Cleaning duplicates, mapping fields and validating imports can be a project phase of its own.

### 5. Reporting

Simple lists are cheap. Filterable dashboards, exports, scheduled reports and historical comparisons require careful data modelling and performance work.

### 6. Non-functional requirements

Expected traffic, uptime, response time, audit logging, data retention, accessibility level and security reviews all add effort. They are also where cheap estimates quietly cut corners.

### 7. Design depth

Using a proven component library is faster than a fully bespoke interface. Both are valid; they cost differently.

## What is usually *not* the main driver

- **The number of pages.** Ten simple pages can be cheaper than one complex scheduling screen.
- **The framework.** React, Next.js or another modern stack rarely changes the total meaningfully; team familiarity matters more.

## How to get an estimate that holds

1. **Write the job, not the features.** Describe who uses the system and what they must accomplish.
2. **Separate must-haves from later.** A smaller first release that works is worth more than a large one that slips.
3. **Pay for discovery.** A short, paid specification phase produces a scope, data model and phased estimate you can compare and own — even if you choose another vendor to build it.
4. **Ask for assumptions in writing.** Every estimate rests on assumptions; make sure you can see them.
5. **Budget for life after launch.** Hosting, monitoring, updates and improvements are ongoing costs, typically agreed as a monthly support plan.

## Comparing proposals

Line up proposals against the same scope document. Check whether each includes testing, deployment, documentation, handover of code and credentials, and a warranty period. A much lower price usually means something on that list is missing.

## Summary

Cost follows complexity: roles, workflow rules, integrations, data and quality requirements. Define those clearly, start with a focused first release, and insist on a written specification before committing to a fixed build price.
